# Aurora connections

The block design contains two one-lane Aurora cores and the logic needed to generate, transmit, receive and check framed data through an external SFP cable. `aurora_64b66b_0` is Aurora 0 / SFP0; `aurora_64b66b_1` is Aurora 1 / SFP1.

## Application data

| Source | Destination | Purpose |
| --- | --- | --- |
| `frame_generator_0/GENERATED_DATA_M_AXIS` | Aurora 0 `USER_DATA_S_AXIS_TX` | Supply payload words for transmission |
| Same TX stream | `golden_reference_fifo_0/TX_MONITOR` | Record words accepted by Aurora 0 |
| Aurora 1 `USER_DATA_M_AXIS_RX` | `frame_checker_0/RX` | Supply received words to the checker |
| FIFO `REF_PORT` | Checker `REF_PORT` | Supply the expected word, keep mask and frame boundary |
| FIFO `OVERFLOW_ERROR` | Checker `FIFO_OVERFLOW_ERROR` | Latch an error if reference storage overflows |
| `aurora_tx_idle_0/M_AXIS` | Aurora 1 `USER_DATA_S_AXIS_TX` | Hold application TX idle with `TVALID = 0` |

Aurora 0 drives TX `TREADY`. The generator advances only when `TVALID && TREADY`; the FIFO monitors that same handshake. The FIFO does not drive `TREADY` and cannot pause Aurora TX. Overflow sets a sticky error.

Aurora's RX interface has no `TREADY`. The checker handles each valid RX word immediately, compares valid bytes plus `TKEEP` and `TLAST`, and consumes a reference word. `ERROR` remains high until reset after a mismatch, missing reference or FIFO overflow. `ERROR_COUNT` counts bad RX words; `RX_FRAME_COUNT` counts received `TLAST` words. Both counters saturate.

> **Source of confusion: Aurora RX is an AXI master.**
> `USER_DATA_M_AXIS_RX` carries data received from the serial link out of the Aurora IP. It is an AXI master because Aurora supplies that stream. `USER_DATA_S_AXIS_TX` is an AXI slave because Aurora accepts the generator's stream for transmission. AXI master/slave names describe the local stream direction; TX/RX names describe the serial-link direction.

`TDATA` is a 64-bit parallel payload bus clocked by `user_clk_out`. `GT_SERIAL_TX` and `GT_SERIAL_RX` are high-speed differential serial interfaces handled by the GTY transceivers; they are not parallel application data ports.

## Application clock, enable and reset

Aurora 0 `user_clk_out` drives:

- Aurora 1 `user_clk`.
- The generator, FIFO and checker `USER_CLK` inputs.
- The idle TX source `USER_CLK` input.
- The ILA sampling clock.

| Logic | Inputs | Output connections |
| --- | --- | --- |
| `util_vector_logic_0`, one-bit AND | Both Aurora `channel_up` outputs | Generator `CHANNEL_UP` |
| `util_vector_logic_1`, one-bit OR | Both Aurora `sys_reset_out` outputs | Generator, FIFO and checker `RESET`; ILA `probe2` |

Both channels must be up before new payload is offered. Either core's system reset clears the application logic and reference FIFO. This application reset is separate from the Aurora startup reset inputs.

## Fixed core control

`core_control_logic_0` drives both Aurora cores through scalar connections:

| Output | Value | Meaning |
| --- | --- | --- |
| `loopback[2:0]` | `3'b000` | Normal external serial operation |
| `power_down` | `1'b0` | Keep the transceiver active |
| `gt_rxcdrovrden_in` | `1'b0` | Use normal CDR control |

Aurora 1 also needs `mmcm_not_locked`, driven by Aurora 0's `mmcm_not_locked_out`. This is a status signal, not another fixed control value.

## Board clocks

| Board source | External interface | Hardware destination |
| --- | --- | --- |
| U47 `USER_SI570_C0`, differential 300 MHz | `default_sysclk_c0_300mhz` | `clk_wiz_0/CLK_IN1_D` |
| U48 `USER_MGT_SI570`, differential 156.25 MHz | `GT_DIFF_REFCLK1_0` | Aurora 0 `GT_DIFF_REFCLK1` |

`clk_wiz_0/clk_out1` supplies 100 MHz to both Aurora `init_clk` inputs and `reset_logic_0/init_clk`. `init_clk` remains running during operation. The Aurora user clock is generated by the GT support logic and is approximately 161.133 MHz for this configuration.

The GT clock interface uses **MGTREFCLK1 of quad X0Y0**. Aurora 0 buffers that differential input and shares its internal reference with Aurora 1.

## Board reset and startup

CPU_RESET pushbutton **SW13** connects through FPGA pin **H11** to external port `reset`. That port drives both `clk_wiz_0/reset` and `reset_logic_0/reset_request`. Clocking Wizard `locked` drives `reset_logic_0/locked`.

The controller asserts reset when the button is pressed or the clock loses lock. Its two-register synchronizer releases the internal reset on the 100 MHz initialization clock. The counter then holds both outputs high for 1024 cycles, releases `pma_init`, waits another 1024 cycles, and releases `reset_pb`. Each interval is approximately 10.24 microseconds.

| Source | Destination |
| --- | --- |
| `reset_logic_0/pma_init` | Aurora 0 `pma_init` |
| Aurora 0 `gt_reset_out` | Aurora 1 `pma_init` |
| `reset_logic_0/reset_pb` | Both Aurora `reset_pb` inputs |

This controller supplies the startup sequence. Cable reconnection, remote-end reset and repeated running-link recovery require separate board verification against the [Aurora duplex reset requirements](https://docs.amd.com/r/en-US/pg074-aurora-64b66b/Aurora-64B/66B-Duplex).

## Shared logic

Aurora 0 owns the reference-clock buffer, QPLL/common resources, clock generation and support reset logic. Aurora 1 uses shared logic outside its IP and receives these signals from Aurora 0:

| Aurora 0 output | Aurora 1 input |
| --- | --- |
| `gt_refclk1_out` | `refclk1_in` |
| `user_clk_out` | `user_clk` |
| `sync_clk_out` | `sync_clk` |
| `mmcm_not_locked_out` | `mmcm_not_locked` |
| `gt_qpllclk_quad1_out` | `gt_qpllclk_quad1_in` |
| `gt_qpllrefclk_quad1_out` | `gt_qpllrefclk_quad1_in` |
| `gt_qplllock_quad1_out` | `gt_qplllock_quad1_in` |
| `gt_qpllrefclklost_quad1_out` | `gt_qpllrefclklost_quad1` |

The two GTY channels use the same quad. Sharing avoids duplicating the common resources. The `quad1` suffix identifies Aurora's first used quad; it does not mean SFP1 or GTY bank 1.

See AMD's [shared-logic description](https://docs.amd.com/r/en-US/pg074-aurora-64b66b/Shared-Logic?contentId=_W55sO_cPfjxlqvuaYc8Ig) and [clock interface](https://docs.amd.com/r/en-US/pg074-aurora-64b66b/Clock-Interface).

## SFP connections

| Core interface | External interface | Board routing |
| --- | --- | --- |
| Aurora 0 `GT_SERIAL_TX` | `sfp0_tx` | SFP0, GTY X0Y0 / quad 127 channel 0 |
| Aurora 0 `GT_SERIAL_RX` | `sfp0_rx` | SFP0, GTY X0Y0 / quad 127 channel 0 |
| Aurora 1 `GT_SERIAL_TX` | `sfp1_tx` | SFP1, GTY X0Y1 / quad 127 channel 1 |
| Aurora 1 `GT_SERIAL_RX` | `sfp1_rx` | SFP1, GTY X0Y1 / quad 127 channel 1 |

These are fixed PCB routes. IP placement selects the GTY channels; XDC constraints assign the external ports to their package pins. A duplex cable connects SFP0 TX to SFP1 RX and SFP1 TX to SFP0 RX. The simulation testbench models those same two paths with assignments.

For board testing, **J39 ON** enables SFP0 TX and **J44 ON** enables SFP1 TX by holding the corresponding `TX_DISABLE` low. Check the SFP modules' rate and control requirements, including rate-select settings, for 10.3125 Gb/s operation.

See [UG1532 GTY routing](https://docs.amd.com/r/en-US/ug1532-zcu670-eval-bd/GTY-Transceivers), [SFP connections](https://docs.amd.com/r/en-US/ug1532-zcu670-eval-bd/zSFP/zSFP-Module-Connectors) and [jumper settings](https://docs.amd.com/r/en-US/ug1532-zcu670-eval-bd/Jumpers).

The authored file is [zcu670_pins.xdc](../Sources/Constraints/zcu670_pins.xdc). The Clocking Wizard has board automation enabled for `default_sysclk_c0_300mhz` and `reset`. Its generated `aurora_system_clk_wiz_0_0_board.xdc` associates these ports with board pins, while `aurora_system_clk_wiz_0_0.xdc` defines the input-clock timing. Vivado scopes the IP ports to the wrapper connections. These files are regenerated under the project's `.gen/` tree.

For the GT reference clock, the authored XDC contains:

```tcl
create_clock -name gt_refclk_156p25 -period 6.400 [get_ports {GT_DIFF_REFCLK1_0_clk_p}]
```

`PACKAGE_PIN` specifies the physical connection. `create_clock` tells timing analysis that the incoming clock has a 6.4 ns period; it does not generate a physical clock. P/N form one differential clock, so the timing clock is defined on P only. The Clocking Wizard already supplies the 300 MHz timing constraint.

Pin assignments can be checked in the installed ZCU670 2.0 board files: `part0_pins.xml` contains package-pin mappings, `board.xml` defines interfaces, and `preset.xml` identifies the SFP GTY sites. In the Xilinx Board Store these are under `boards/Xilinx/zcu670/2.0/`. Also see [UG1532 Clock Generation](https://docs.amd.com/r/en-US/ug1532-zcu670-eval-bd/Clock-Generation) and [User I/O](https://docs.amd.com/r/en-US/ug1532-zcu670-eval-bd/User-I/O). The board guide's clock, GTY and jumper tables provide the corresponding schematic references.

## ILA

`ila_0` uses Aurora 0 `user_clk_out` and samples 1024 entries. Its probes are:

| Probe | Width | Signal |
| --- | --- | --- |
| `probe0` | 1 | Aurora 0 `channel_up` |
| `probe1` | 1 | Aurora 1 `channel_up` |
| `probe2` | 1 | Common application reset |
| `probe3` | 1 | Checker `ERROR` |
| `probe4` | 32 | Checker `ERROR_COUNT` |
| `probe5` | 32 | Checker `RX_FRAME_COUNT` |
| `probe6` | 1 | FIFO `OVERFLOW_ERROR` |

A working data path should show both channels up, reset low, no checker/FIFO errors and an increasing frame counter. The GT-derived sampling clock can stop during transceiver reset. The automatically inserted debug hub is separate from the ILA sampling logic; its clock behavior during reset still needs board verification. See [AMD's debug-clock requirements](https://docs.amd.com/r/2025.2-English/ug908-vivado-programming-debugging/Debug-Core-Clocks).
